# GitHub Actions Secrets and R2 Configuration Guide

This document is aimed at users deploying this project for the first time. It explains where to obtain each Secret in GitHub Actions, how to fill it in, and the difference between using a shared token or separate tokens for the two R2 buckets `qingyu-music` and `qingyu-media`.

> 📘 **A more complete beginner tutorial**: account registration, creating D1 / KV, ticking API token permissions, R2 CORS and custom domains, Workers AI, binding a domain, post-deployment self-checks, the troubleshooting quick-reference table and free-tier limits are all in
> **[CLOUDFLARE_SETUP_GUIDE_EN.md](CLOUDFLARE_SETUP_GUIDE_EN.md)**. This document can be seen as a detailed explanation of the "Secrets and R2 tokens" part of it.

> To state the conclusion first: the current version only needs one set of R2 S3 credentials. The most reliable approach for beginners is to create a shared token that has "Object Read & Write" permission on both buckets. The current workflow and signing code do not yet read two separate sets of R2 credentials.

For this music upload fix, the GitHub Secret names have not changed, and the Cloudflare bucket names, public domains and existing token permissions do not need to change because of the code fix. What does need confirming is that the token currently behind `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` must be able to write to the bucket that music uploads actually use.

## 1. First, Separate the Four Kinds of Configuration

| Configuration | Where it goes | Purpose |
| --- | --- | --- |
| GitHub Actions Secrets | The repository's `Settings → Secrets and variables → Actions → Secrets` | The current workflow reads only from here; names must match exactly |
| GitHub Actions Variables | The `Variables` tab of the same page | The current workflow does not read these; filling them in here has no effect |
| Cloudflare Account API Token | Filled into GitHub Secrets as `CLOUDFLARE_API_TOKEN` | Used by Wrangler to deploy the Worker, run D1 migrations, etc. |
| R2 S3 credentials | Access Key ID and Secret Access Key filled into `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` respectively | Used by the Worker to sign R2 direct-upload addresses for browsers |

The easiest things to confuse are the Cloudflare API Token and the R2 S3 credentials:

- The Cloudflare API Token is `CLOUDFLARE_API_TOKEN`, usually displayed as an ordinary token string.
- R2 S3 credentials are generated by an R2 API token and contain a pair of `Access Key ID` and `Secret Access Key`, corresponding to two different GitHub Secrets.

## 2. Five Rules You Must Know for the Current Version

1. All configuration must be added to GitHub `Secrets`, not to `Variables`.
2. There is currently only one set of R2 credentials: `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`.
3. `R2_BUCKET` must not be empty. The workflow writes the R2 configuration into the Worker only when the R2 credentials, the Endpoint and `R2_BUCKET` all exist.
4. Music upload currently prefers `R2_BUCKET`. Only when the music bucket name or the music public domain is not configured does it fall back to `R2_MEDIA_BUCKET`.
5. After changing a GitHub Secret you must re-run the deployment workflow for the Worker's runtime Secret to be updated.

These behaviours come from:

- [.github/workflows/deploy.yml](.github/workflows/deploy.yml)
- [functions/_lib/music.js](functions/_lib/music.js)
- [functions/_lib/media.js](functions/_lib/media.js)

## 3. Adding Entries in GitHub

1. Open the repository home page.
2. Go to `Settings`.
3. On the left, choose `Secrets and variables → Actions`.
4. Choose the `Secrets` tab and click `New repository secret`.
5. Enter the name and the value, then click `Add secret`.
6. Repeat for every Secret listed in this document.

When filling them in, note:

- Names are case-sensitive; for example it must be `R2_MEDIA_BUCKET`.
- Enter only the value, not `R2_MEDIA_BUCKET=...`.
- Normally do not wrap the value in quotes.
- After saving, the original value can no longer be viewed; it can only be set again.
- The current workflow does not specify a GitHub Environment, so repository-level Repository secrets are preferred.

## 4. Required Secrets

If any of these four is missing, the deployment stops immediately.

| Secret | What to enter | Example format |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | Cloudflare Account API Token | Copy the complete token after creating it in Cloudflare |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID | `a1b2c3d4e5f678901234567890abcdef` |
| `BLOG_D1_ID` | D1 database ID, not the database name | `0fa366ac-f04a-4be2-8e11-5adc6ee6d686` |
| `BLOG_KV_ID` | KV Namespace ID | A 32-character hexadecimal string |

`CLOUDFLARE_API_TOKEN` needs at least the following permissions:

| Permission scope | Permission | Reason |
| --- | --- | --- |
| Account / Workers Scripts | Edit | Deploy the Worker |
| Account / D1 | Edit | Run D1 migrations before deployment |
| Account / Workers KV Storage | Edit | Deploy the KV binding |
| Zone / Cache Purge | Purge | Optional; used together with `CF_ZONE_ID` to purge the cache on publish |

If you use the broader "Administrator Read & Write" Account API Token that Cloudflare provides, it can also complete the current deployment, but for production it is better to create one with least privilege.

## 5. Recommended and Optional Secrets

| Secret | Required? | Filling advice |
| --- | --- | --- |
| `BLOG_ADMIN_SETUP_KEY` | Recommended | A sufficiently long random string. Once configured, the first initialisation must supply the setup key, preventing anyone else from initialising the administrator first |
| `SITE_URL` | Recommended | The site's official address, e.g. `https://www.example.com`. Do not add a trailing `/` |
| `CF_ZONE_ID` | Optional | The ID of the Cloudflare Zone that hosts the site domain; it must be used together with the Cache Purge permission of `CLOUDFLARE_API_TOKEN` |
| `PAGES_PROJECT_NAME` | Optional | Its actual meaning is the Worker name. When left empty, the repository default name `kejiland` is used. Renaming it arbitrarily may deploy a different Worker, so beginners are advised to leave it empty |
| `BLOG_WRITE_TOKEN` | Optional | Legacy write token. New deployments normally do not need to fill it in |
| `BLOG_RATE_LIMIT_BINDING` | Optional | A positive integer (such as `1001`). Filling it in enables the in-Worker edge login rate limiting and makes the deployment switch to wrangler 4.x (this binding requires ≥ 4.36). If your account does not support the binding, delete this Secret and redeploy to recover |

### 5.1 Three Runtime Variables to Care About After Deployment

These three are **not GitHub Secrets**, but they are easily confused with the table above:

| Variable | Who writes it | Effect | When unset |
| --- | --- | --- | --- |
| `CF_API_TOKEN` | **Written automatically by the workflow** (value taken from `CLOUDFLARE_API_TOKEN`) | Calls the Cloudflare Cache Purge API to clear the edge cache after a post is published | No cache purging (functionality is unaffected; new content may just take 1~5 minutes to take effect) |
| `BLOG_AI_ENABLED` | **You must set it manually** (dashboard → Worker → Settings → Variables and Secrets, or `npx wrangler secret put BLOG_AI_ENABLED --name kejiland`) | Set to `0` / `false` / `off` to switch AI off entirely | Treated as enabled when Workers AI is bound and D1 exists |
| `BLOG_AI_PUBLIC` | As above, set manually | Set to `0` / `false` / `off` to forbid anonymous visitors from generating AI summaries (still available after logging in) | Anonymous generation is allowed |

> Only `CF_API_TOKEN` is written automatically by the workflow. It is fine not to set the other two: as long as the deployment succeeds and `/api/ai/ping` returns `{"ok":true}`, that means AI is available.

## 6. R2 Bucket Preparation

It is recommended to prepare two buckets:

| Purpose | Example bucket name | Example public read domain |
| --- | --- | --- |
| Music | `qingyu-music` | `https://music.example.com` |
| Image media | `qingyu-media` | `https://media.example.com` |

Every bucket must complete:

1. Create the bucket in Cloudflare R2.
2. Bind your own domain under the bucket's `Settings → Public access → Custom Domains`.
3. Confirm that the public domain can read objects inside the bucket directly.
4. Allow the site origin to perform uploads in the bucket's CORS settings.

For browser direct uploads, the CORS settings should contain at least:

| Setting | Recommended value |
| --- | --- |
| Allowed Origins | `https://www.example.com`, replaced with your `SITE_URL` |
| Allowed Methods | `PUT`, `GET`, `HEAD` |
| Allowed Headers | `Content-Type` |
| Expose Headers | `ETag` |
| Max Age | `3600` |

If the site uses both `example.com` and `www.example.com`, both origins must be added to Allowed Origins.

## 7. R2 Secrets Summary Table

| Secret | What to enter |
| --- | --- |
| `R2_ACCESS_KEY_ID` | The Access Key ID from the R2 API Token result |
| `R2_SECRET_ACCESS_KEY` | The Secret Access Key from the R2 API Token result, shown only once at creation time |
| `R2_ENDPOINT` | `https://<CLOUDFLARE_ACCOUNT_ID>.r2.cloudflarestorage.com` |
| `R2_BUCKET` | Music bucket name, e.g. `qingyu-music` |
| `R2_PUBLIC_BASE` | Music bucket public read address, e.g. `https://music.example.com` |
| `R2_MEDIA_BUCKET` | Media bucket name, e.g. `qingyu-media` |
| `R2_MEDIA_PUBLIC_BASE` | Media bucket public read address, e.g. `https://media.example.com` |

Notes on `R2_ENDPOINT`:

- It does not contain the bucket name.
- It does not end with `/`.
- It is not the R2 custom public domain.
- Correct example: `https://a1b2c3d4e5f678901234567890abcdef.r2.cloudflarestorage.com`

Notes on the public domain base:

- It must start with `https://`.
- Do not add a trailing `/`.
- Enter the custom domain bound to the corresponding bucket, not the R2 S3 Endpoint.

## 8. Recommended Approach: One Token Shared by Both Buckets

This is the configuration best suited to beginners in the current version.

### 8.1 Creating a Shared R2 Token in Cloudflare

1. Go to Cloudflare `R2 → API → Manage API Tokens`.
2. Create a new API Token.
3. For the permission choose `Object Read & Write`; the Chinese interface normally shows this label in Chinese.
4. For the scope, select both `qingyu-music` and `qingyu-media`.
5. If the interface only allows a single bucket to be selected, select all buckets, or check again whether the current Cloudflare page supports multiple selection. Do not keep using an old Token that is authorised for only one bucket.
6. Immediately after creating it, save the Access Key ID, the Secret Access Key and the Endpoint.

Do not modify or replace the Cloudflare Account API Token that is currently used for deployment. The shared R2 Token is a separate set of S3 credentials.

### 8.2 What to Fill In on GitHub

| Secret | Example |
| --- | --- |
| `R2_ACCESS_KEY_ID` | Access Key ID of the shared R2 Token |
| `R2_SECRET_ACCESS_KEY` | Secret Access Key of the shared R2 Token |
| `R2_ENDPOINT` | `https://your-account-id.r2.cloudflarestorage.com` |
| `R2_BUCKET` | `qingyu-music` |
| `R2_PUBLIC_BASE` | `https://music.example.com` |
| `R2_MEDIA_BUCKET` | `qingyu-media` |
| `R2_MEDIA_PUBLIC_BASE` | `https://media.example.com` |

### 8.3 Where the Current Code Actually Writes

A shared Token can access both buckets at the same time, and the current version writes to each bucket according to its purpose:

| Upload type | Current actual target bucket |
| --- | --- |
| Image media | `R2_MEDIA_BUCKET` |
| Music | Prefers `R2_BUCKET`; falls back to `R2_MEDIA_BUCKET` when the music bucket configuration is incomplete |

Therefore a shared Token must have object read and write permission on both buckets at once. After configuring as described in this document, music goes into `qingyu-music` and images go into `qingyu-media`.

## 9. Using Only One Bucket

### 9.1 Only Image Media, No Music Upload

Even if you do not enable the music feature, you must still fill in `R2_BUCKET` and `R2_PUBLIC_BASE`, otherwise the workflow will not write this set of R2 credentials.

| Secret | Value to enter |
| --- | --- |
| `R2_ACCESS_KEY_ID` | An Access Key ID with object read and write permission on the media bucket |
| `R2_SECRET_ACCESS_KEY` | The corresponding Secret Access Key |
| `R2_ENDPOINT` | R2 Endpoint |
| `R2_BUCKET` | `qingyu-media` |
| `R2_PUBLIC_BASE` | `https://media.example.com` |
| `R2_MEDIA_BUCKET` | `qingyu-media` |
| `R2_MEDIA_PUBLIC_BASE` | `https://media.example.com` |

### 9.2 Only Music, No Image Media

| Secret | Value to enter |
| --- | --- |
| `R2_ACCESS_KEY_ID` | An Access Key ID with object read and write permission on the music bucket |
| `R2_SECRET_ACCESS_KEY` | The corresponding Secret Access Key |
| `R2_ENDPOINT` | R2 Endpoint |
| `R2_BUCKET` | `qingyu-music` |
| `R2_PUBLIC_BASE` | `https://music.example.com` |
| `R2_MEDIA_BUCKET` | Leave empty |
| `R2_MEDIA_PUBLIC_BASE` | Leave empty |

In this case music uploads work, while the image media upload endpoint returns 503.

### 9.3 One Bucket Shared by Both Features

Let music and images use the same bucket:

| Secret | Value to enter |
| --- | --- |
| `R2_BUCKET` | `qingyu-media` |
| `R2_PUBLIC_BASE` | `https://media.example.com` |
| `R2_MEDIA_BUCKET` | `qingyu-media` |
| `R2_MEDIA_PUBLIC_BASE` | `https://media.example.com` |

The Token only needs object read and write permission on this bucket.

## 10. Separate Tokens for the Two Buckets

The current version does not support configuring two sets of R2 credentials directly in GitHub.

The reasons are:

- The workflow reads only `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`.
- All upload and delete signatures use this same set of credentials.
- Even if a `qingyu-music` Token has already been created, there is no corresponding GitHub Secret to put it in.

Do not concatenate the two Tokens into JSON, text or any other format and stuff them into the existing Secret. The current code will treat it as an ordinary Access Key ID or Secret Access Key, and signing will still fail.

If separate Tokens are really needed later, the code must be changed at the same time:

| Secret planned to be added | Purpose |
| --- | --- |
| `R2_MUSIC_ACCESS_KEY_ID` | Music bucket Access Key ID |
| `R2_MUSIC_SECRET_ACCESS_KEY` | Music bucket Secret Access Key |
| `R2_MEDIA_ACCESS_KEY_ID` | Media bucket Access Key ID |
| `R2_MEDIA_SECRET_ACCESS_KEY` | Media bucket Secret Access Key |

Also to be modified:

1. The deployment workflow, so that the four new values are written into the Worker.
2. `presignPut`, so that the corresponding Access Key ID and Secret are chosen according to the target bucket.
3. Delete-signing logic such as `sigv4AuthHeader` and `r2DeleteObject`.
4. The related tests, covering uploads to and deletes from each of the two buckets.

Until these changes are complete, continue using the shared Token.

## 12. Post-Deployment Verification

1. Go to the `Actions` tab of the GitHub repository.
2. Select `Deploy to Cloudflare Workers`.
3. Click `Run workflow`, choose `main` and run it.
4. Wait for the deployment to succeed.
5. Open the admin panel and upload an image and an audio file separately.
6. Click the public address to confirm the file can be played or displayed.

Common problems:

| Symptom | Common cause |
| --- | --- |
| Actions reports missing required Secrets | They were filled into Variables, or the name is misspelled |
| Image or music upload returns 503 | The R2 variables are incomplete; in particular check whether `R2_BUCKET` is empty |
| Browser upload returns 403 | The R2 Token has no write permission on the target bucket, the Endpoint is wrong, the Access Key and Secret do not match, or the bucket CORS does not allow the site origin |
| Upload succeeds but playback returns 404 | The public domain is not bound to the corresponding bucket, or `R2_PUBLIC_BASE` / `R2_MEDIA_PUBLIC_BASE` is filled in incorrectly |
| The Secret was changed but nothing changed online | The deployment workflow was not re-run |
| Music is still written to the media bucket | Check whether both `R2_BUCKET` and `R2_PUBLIC_BASE` are filled in; when the music bucket configuration is incomplete it falls back to the media bucket |

## 13. Common Confusion: Which Set of R2 Tokens Should I Use?

Many people end up creating several R2 Tokens in Cloudflare and then are unsure which one to put into GitHub. The way to decide is simple:

| Situation | Which one to fill in |
| --- | --- |
| You created only one R2 Token, its permission is "Object Read & Write" and it covers both buckets | ✅ Fill in that one; this is the most recommended approach |
| You created two Tokens, each authorised for only one bucket | ⚠️ The current version **supports only one set of credentials** and cannot fill them in separately. Create a Token that authorises both buckets instead (see [section 8](#8-recommended-approach-one-token-shared-by-both-buckets)) |
| You have an old Token authorised only for `qingyu-media` | ⚠️ It will make music uploads return 403. Either change its permission to cover both buckets, or create a new shared Token |
| You have a Token authorised only for `qingyu-music` | ❌ It does not match this project's shared-credential approach; do not fill it in |

Filling and updating rules:

- Music is uploaded to `R2_BUCKET` (which requires `R2_PUBLIC_BASE` to be configured as well), and images are uploaded to `R2_MEDIA_BUCKET`;
- Whenever any Access Key ID / Secret Access Key changes, you must **update in sync** the GitHub `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`, and **re-run the deployment workflow once**;
- If you really want each of the two buckets to use a separate Token, you must first complete the code and workflow changes described in [section 10](#10-separate-tokens-for-the-two-buckets); this is not supported yet.

## 14. Recommended Configuration Checklist for Beginners

1. Create the two buckets `qingyu-music` and `qingyu-media`.
2. Bind a public custom domain to each of the two buckets.
3. Create one shared R2 Token that has object read and write permission on both buckets.
4. Fill in every name listed in this document in GitHub `Secrets`.
5. Configure `BLOG_ADMIN_SETUP_KEY` and `SITE_URL`.
6. Do not fill in `PAGES_PROJECT_NAME`; keep the default Worker name.
7. Push the code or run the deployment manually from `Actions`.
8. After the deployment completes, test image and music uploads separately.
